# Legacy Business Rules

レガシーコードベースからビジネスルール仕様書(What 部分)を復元するスキル。新規作り直しの要件定義のインプットを作ることが目的。`legacy-feature-inventory` の後工程にあたる。

## 前提条件

- 入手できる情報は**ソースコードのみ**(ドキュメントなし、コメントなし、git 履歴なし)
- 開発者へのヒアリング・実機での動的解析はできない
- 機能一覧(`legacy-feature-inventory` の成果物)が存在すること。なければ先にそちらを実行する

## 基本原則

1. **What のみを記述する**。「いつ・どの条件で・何をするか」はコードから確定できる。「なぜそのルールなのか」は復元できないため、Why 欄は「不明」と明記して残す(勝手に理由を創作しない)
2. **すべてのルールに確信度を付ける**: `確定` / `推測` / `不明`(機能一覧スキルと同じ 3 値)
3. **ルール ID は機能 ID に紐付ける**(`F-001` → `BR-001-01`)。機能一覧と相互参照可能にし、抜け漏れを検証できるようにする
4. **多重実装の食い違いはノイズではなく一級の発見**として記録する。新システムでどちらを正とするかは要件定義の論点になる
5. ルールの自然言語化には機能一覧の業務用語集の語彙を優先して使う

## ワークフロー

進捗チェックリストとして使うこと:

```
- [ ] Phase 0: 入力確認とスコープ設定
- [ ] Phase 1: ルールの発掘
- [ ] Phase 2: メッセージ起点の逆引き
- [ ] Phase 3: 分類
- [ ] Phase 4: 表現形式への正規化
- [ ] Phase 5: 暗黙ルールの捕捉
- [ ] Phase 6: 多重実装の突合
- [ ] Phase 7: 成果物の出力
```

### Phase 0: 入力確認とスコープ設定

1. 機能一覧の成果物を読み込み、対象とする機能 ID の範囲を決める(全機能 or ユーザー指定の機能群)
2. 機能一覧の「エントリポイント」「関連テーブル」欄を起点リストにする
3. 業務用語集を読み込み、ルール記述の語彙として使う

### Phase 1: ルールの発掘

機能ごとに、エントリポイントから到達するコードを [rule-patterns.md](rule-patterns.md) の生息場所パターンで走査する。対象は大きく 5 系統:

1. 入力検証(保存・確定前のチェック)
2. 業務データによる条件分岐
3. 計算ロジック(金額・数量・日付)
4. 状態遷移(status / flag カラムの読み書き)
5. DB 側のルール(制約・DEFAULT・トリガー・ストアドプロシージャ)

### Phase 2: メッセージ起点の逆引き

コメントなし環境で最も効率の良い抽出経路。**必ず実施する**。

1. エラー・確認メッセージ(MsgBox / MessageBox.Show / ShowMessage 等)を全列挙する
2. 各メッセージについて、それを表示させる**条件式まで遡る**
3. メッセージ文がルールの自然言語表現、条件式がルール定義になる
   (例: `「締め処理後は変更できません」` + `If closed_flg = 1` → ルール「締め処理済みの受注は変更できない」)
4. Phase 1 で見つけた分岐と突合し、**メッセージのない暗黙の拒否・スキップ**(silent return / 何も言わず処理しない)も漏らさず拾う

### Phase 3: 分類

発掘したルールを 4 種別に振り分ける(Ross / von Halle の分類を簡略化):

| 種別 | 内容 | 例 |
|---|---|---|
| 制約 | 〜の場合、〜してはならない/〜でなければならない | 締め後の変更禁止、限度額チェック |
| 導出 | 〜は〜から計算される | 売価 = 単価 × 数量 × (1 - 掛率) |
| 状態遷移 | 状態 X から Y へは条件 Z のとき遷移する | 受注 → 出荷済 は引当完了時のみ |
| 定義 | 用語・コード値の定義 | 顧客区分 3 = 特価対象(推測) |

### Phase 4: 表現形式への正規化

種別と複雑さに応じて表現を選ぶ:

| 対象 | 表現形式 |
|---|---|
| 単一条件のルール | 条件文 1 行(「〜の場合、〜する」) |
| 複合条件(ネストした if、3 条件以上) | ディシジョンテーブル |
| 計算 | 計算式仕様(式 + 端数処理 + 桁数 + 0除算等の例外時挙動のセット) |
| 状態遷移 | 状態遷移表 |

フォーマットは [output-template.md](output-template.md) に従う。ネストした if をそのまま散文に翻訳しない。表に正規化することで、コードを読まない人が検証できる形にする。

### Phase 5: 暗黙ルールの捕捉

字面に書かれていないが業務仕様として効いているものを、rule-patterns.md の「暗黙ルールチェックリスト」で機能ごとに確認する。代表例:

- **端数処理**(VB6 / VB.NET の `Round` は銀行丸め。金額計算の丸め方は業務仕様そのもの)
- 暗黙の型変換、`On Error Resume Next` 下で継続した場合のデフォルト値
- 日付境界(「以上」か「より大きい」か、時刻部分の扱い)
- DB の DEFAULT 値・トリガーによる自動補完

### Phase 6: 多重実装の突合

同一ルールが複数レイヤー(UI 検証 / 保存前チェック / DB 制約 / ストアド)に実装されていないか突合する。

1. ルールごとに実装箇所を全列挙する(Phase 1 の走査結果と CRUD マトリクスを使う)
2. 条件が**一致**する場合: 多重実装欄に併記(確信度を上げる根拠になる)
3. 条件が**食い違う**場合: 矛盾リストに記録し、要調査リストへ転記する(どちらが正かはコードから判断できない)

### Phase 7: 成果物の出力

[output-template.md](output-template.md) のフォーマットで出力する。構成:

1. 調査サマリ(対象機能数・ルール数・確信度の分布・矛盾件数)
2. ルール一覧(本体、機能 ID 紐付け)
3. ディシジョンテーブル / 計算式仕様 / 状態遷移表(別添)
4. 多重実装・矛盾リスト
5. 要調査リスト(Why 不明事項、矛盾、未入手のストアド等)

## 完了前チェックリスト

- [ ] 全メッセージ文字列がいずれかのルールに紐付いているか(未紐付けは取りこぼしの兆候)
- [ ] 機能一覧の全対象機能に最低 1 つのルールまたは「ルールなし(確定)」の記載があるか
- [ ] 計算式仕様に端数処理の記載が漏れていないか
- [ ] status / flag カラムを持つテーブルに状態遷移表があるか
- [ ] Why 欄に推測の理由を書いていないか(理由の創作は禁止。書くなら「推測:」と明示)
