# Output Template — ビジネスルール仕様書フォーマット

成果物は 1 つの markdown ファイル(例: `business-rules.md`)にまとめる。構成は以下の 5 セクション。

確信度は `legacy-feature-inventory` と共通の 3 値: `確定` / `推測` / `不明`

ルール ID の形式: `BR-<機能ID連番>-<ルール連番>`(例: 機能 F-001 のルールは BR-001-01, BR-001-02, …)
複数機能にまたがる共通ルールは `BR-COM-01` とし、適用機能欄に機能 ID を列挙する。

---

## 1. 調査サマリ

```markdown
# ビジネスルール仕様書 — [システム名]

## 調査サマリ

- 調査日:
- 入力: 機能一覧 [ファイル名] の F-XXX〜F-XXX(XX 機能)
- 抽出ルール数: XX(制約 XX / 導出 XX / 状態遷移 XX / 定義 XX)
- 確信度分布: 確定 XX / 推測 XX / 不明 XX
- 多重実装の矛盾: XX 件
- 未調査領域: [未入手のストアド、ソースなし DLL 等]
```

## 2. ルール一覧(本体)

```markdown
## ルール一覧

| ID | 機能ID | 種別 | ルール文(What) | 条件の詳細 | 実装箇所 | 多重実装 | Why | 確信度 |
|---|---|---|---|---|---|---|---|---|
| BR-001-01 | F-001 | 制約 | 締め処理済みの受注は変更できない | T_ORDER.closed_flg = 1 のとき更新を拒否しエラー表示 | frmOrder.frm: cmdSave_Click | usp_UpdOrder にも同等チェック(条件一致) | 不明 | 確定 |
| BR-001-02 | F-001 | 導出 | 受注金額の算出 → 計算式仕様 CALC-01 | (別添参照) | frmOrder.frm: CalcTotal | なし | 不明 | 確定 |
| BR-001-03 | F-001 | 制約 | 顧客コード 9999 は与信チェックをスキップする | custCode = "9999" のとき CheckCredit を呼ばない | frmOrder.frm: cmdSave_Click | なし | 不明(特定顧客の特例。理由の手がかりなし) | 確定 |
| BR-002-01 | F-002 | 定義 | 顧客区分 3 = 特価適用対象 | cust_type = 3 のとき M_PRICE を参照 | frmOrder.frm: Form_KeyDown | なし | 不明 | 推測 |
```

記載ルール:

- ルール文は機能一覧の業務用語集の語彙で書く。「〜の場合、〜する/〜してはならない」の形を基本にする
- 実装箇所は `ファイル名: 関数/ハンドラ名` 形式(検証可能にするため必須)
- 条件が 3 つ以上絡む場合はルール文に詳細を書かず、別添のディシジョンテーブル ID を参照する
- Why 欄は原則「不明」。手がかりがある場合のみ「推測: 〜」と明示して書く(理由の創作は禁止)
- 検証した結果ルールが存在しない機能も「F-XXX: ルールなし(確定)」と明記する(未調査と区別するため)

## 3. 別添: 複合ルールの詳細

### ディシジョンテーブル(複合条件)

```markdown
### DT-01: 受注時の承認要否(BR-003-01)

| # | 条件: 受注金額 | 条件: 顧客区分 | 条件: 与信残 | → 結果 |
|---|---|---|---|---|
| 1 | 100万円以上 | - | - | 承認必須 |
| 2 | 100万円未満 | 新規(=1) | - | 承認必須 |
| 3 | 100万円未満 | 既存 | 不足 | 承認必須 |
| 4 | 100万円未満 | 既存 | 充足 | 承認不要 |

- 実装箇所: frmOrder.frm: NeedApproval
- 網羅性: コード上の else に該当する行 = #4(暗黙のデフォルト)
```

### 計算式仕様(導出ルール)

端数処理・桁数・例外時挙動を必ずセットで書く:

```markdown
### CALC-01: 受注金額(BR-001-02)

- 式: 明細金額 = 単価 × 数量 × (1 - 掛率/100)、受注金額 = Σ明細金額 + 消費税
- 端数処理: 明細ごとに円未満を Round で丸め(**銀行丸め**)、合計後に消費税計算
- 消費税: Int(合計 × 税率) — 切り捨て。税率は M_CONFIG.tax_rate から取得
- 例外時挙動: 掛率が NULL のとき 0 として計算(Nz による暗黙デフォルト)
- 実装箇所: frmOrder.frm: CalcTotal
- 確信度: 確定
```

### 状態遷移表

```markdown
### ST-01: 受注ステータス(T_ORDER.status)

| 遷移前 → 遷移後 | 契機(機能ID) | ガード条件 | 実装箇所 | 確信度 |
|---|---|---|---|---|
| 1(受付) → 2(引当済) | F-005 在庫引当 | 在庫数 >= 受注数 | mdlStock.bas: Allocate | 確定 |
| 2(引当済) → 3(出荷済) | F-006 出荷登録 | なし(**ガードなし。どの状態からでも 3 に更新可能**) | frmShip.frm: cmdShip_Click | 確定 |

- コード値の意味(1=受付 等)の根拠: [UI文字列 / 推測] 
- 図が必要な場合は mermaid の stateDiagram を併記してよい
```

## 4. 多重実装・矛盾リスト

```markdown
## 多重実装・矛盾リスト

| # | ルールID | レイヤーA | レイヤーB | 食い違いの内容 | 影響 |
|---|---|---|---|---|---|
| 1 | BR-004-01 | frmOrder: 限度額 100万 | usp_ChkOrder: 限度額 300万 | 閾値が不一致(UI が先に弾くため DB 側は実質死んでいる可能性) | どちらが正か要確認 |
| 2 | BR-007-02 | frmA: 全角チェックあり | frmB(コピペ元): チェックなし | 同じ項目の検証が画面によって異なる | 入力経路により不整合データが存在しうる |
```

矛盾は必ず要調査リストにも転記する。

## 5. 要調査リスト

