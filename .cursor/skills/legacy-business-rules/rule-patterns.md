# Rule Patterns — ルールの生息場所と暗黙ルール

ビジネスルールがコードのどこに隠れているかのパターン集。Phase 1 / 2 / 5 の走査で使う。
grep パターンの言語別の具体形は `../legacy-feature-inventory/language-map.md` を参照する。ファイルが見つからない場合は `legacy-feature-inventory` スキルの language-map.md を探す。それもなければ代表的なファイルを 1 つ精読して言語別の具体形を特定してから走査する(未知の言語への対応と同じ進め方)。

## 1. 入力検証(制約ルールの最大の生息地)

| 場所 | 見つけ方 |
|---|---|
| 保存・確定ボタンのハンドラ冒頭 | Click ハンドラ内の if + メッセージ + Exit/return の連なり |
| フォーカス喪失時の検証 | `Validating` / `LostFocus` / `Exit` イベント |
| 入力中の制限 | `KeyPress` / `Change` イベント内の入力拒否(数字のみ等) |
| UI コントロールのプロパティ | MaxLength、リストの選択肢自体が制約のことがある |

注意: UI プロパティによる制約(桁数制限など)はコード上に if 文として現れないため見落としやすい。画面定義ファイルも走査対象に含める。

## 2. 業務データによる条件分岐

| 場所 | 見つけ方 |
|---|---|
| コード値での分岐 | `Select Case` / `switch` / if の比較対象がマスタのコード値カラム |
| 顧客・商品・拠点ごとの特例 | 特定 ID・コードのハードコード比較(`If custCode = "9999"`)— 特例ルールの典型 |
| 日付による分岐 | システム日付との比較、年度・月跨ぎの判定 |
| フラグによる機能のオンオフ | 設定テーブル・INI・レジストリ値での分岐(設定駆動ルール) |

ハードコードされた特定値との比較は最重要。「なぜこの値か」が失われた特例ルールの化石であることが多い。必ず Why 不明として記録する。

## 3. 計算ロジック

| 場所 | 見つけ方 |
|---|---|
| 金額・数量計算 | 算術演算が集まっている関数、`Calc` / `Compute` / `Get○○Amount` 系の命名 |
| 消費税・掛率・手数料 | 定数または設定値との乗算 |
| 日付計算 | 締め日・支払日・有効期限の加算ロジック |
| SQL 内の計算 | SELECT 句・ストアド内の演算式(コード側に現れない) |

計算式は「式」だけでなく**端数処理・桁数・計算順序**まで必ずセットで記録する(下記の暗黙ルールチェックリスト参照)。

## 4. 状態遷移

| 場所 | 見つけ方 |
|---|---|
| status / flag カラム | テーブル定義から `status` `state` `flg` `kbn` 等のカラムを列挙 → そのカラムへの UPDATE を全 grep |
| 遷移の条件 | UPDATE の前後の if 文(遷移ガード条件) |
| 不正遷移の防止 | 「現在の状態が X のときだけ実行」のチェック。**チェックがない遷移も記録する**(どこからでも遷移可能、が仕様か漏れかは不明として) |

status カラムごとに「全 UPDATE 箇所 × 遷移前後の値 × ガード条件」を集めると状態遷移表が機械的に作れる。

## 5. DB 側のルール

この年代のアプリはロジックの相当部分が DB 側にある。**コードだけ読んで完了としない**。

| 場所 | 内容 |
|---|---|
| CHECK 制約・UNIQUE 制約・FK | 宣言的なルール(確定として記録できる) |
| DEFAULT 値 | 暗黙の初期値ルール |
| トリガー | 自動補完・自動計算・履歴記録。アプリコードからは完全に不可視 |
| ストアドプロシージャ・関数 | 計算・検証ロジック本体。未入手なら要調査リストへ |
| ビュー | 暗黙の絞り込み条件(WHERE 句)が「見えるデータの定義」というルール |

## 6. メッセージ(Phase 2 の起点)

| 種類 | ルールとしての意味 |
|---|---|
| エラーメッセージ | 制約ルールの自然言語表現(最良の情報源) |
| 確認メッセージ(はい/いいえ) | 条件付きで許可される操作。「いいえ」側の分岐も読む |
| 警告して続行 | ソフト制約(推奨ルール) |
| **メッセージなしの silent return** | 暗黙の拒否。grep では拾えないため、検証ロジック走査時に意識して探す |

## 暗黙ルールチェックリスト(Phase 5)

機能ごとに以下を確認する。字面にルールとして書かれていないが、新システムで挙動が変わると業務事故になる項目。

- [ ] **端数処理**: 丸めはどの方式か。VB6 / VB.NET の `Round` は銀行丸め(偶数丸め)であり、四捨五入ではない。`Int` / `Fix` は負数で挙動が違う。`CInt` `CLng` も銀行丸め
- [ ] **計算順序と途中桁数**: 乗算と丸めの順序(明細ごとに丸めてから合計か、合計後に丸めるか)
- [ ] **整数除算と型変換**: `\` と `/`(VB)、int / int(C 系)の切り捨て。Variant / Object 型の暗黙変換
- [ ] **日付境界**: `>=` か `>` か。日付比較に時刻部分が含まれるか。月末日の扱い(31日締めの2月)
- [ ] **NULL / 空文字 / 0 の扱い**: 未入力をどう解釈しているか。`Nz` / `IsNull` / `IIf` のデフォルト値
- [ ] **エラー時の継続挙動**: `On Error Resume Next` / 空 catch の範囲内で失敗した処理は「失敗しても続行する」が仕様化している可能性。どこまで進んでコミットされるか
- [ ] **文字列比較**: 大文字小文字・全角半角・前後空白の扱い(`Option Compare Text`、Trim の有無)
- [ ] **DB の DEFAULT・トリガー**: アプリが書かない値を誰が入れているか
- [ ] **処理順序そのもの**: 複数テーブル更新の順序とトランザクション境界(途中で落ちた場合に何が残るか)

## 多重実装の典型箇所(Phase 6)

同一ルールが重複しやすいレイヤーの組み合わせ:

1. UI の入力検証 ↔ 保存処理内の再チェック
2. アプリ側チェック ↔ DB の CHECK / UNIQUE 制約
3. アプリ側計算 ↔ ストアド内計算(片方だけ修正されて食い違うのが典型)
4. 複数画面に同じ検証のコピペ(片方だけ改修されているパターン。継ぎ足し開発の典型)

突合の手順: ルールごとに条件式を正規化して比較し、不一致(閾値違い・条件の抜け・丸め方式違い)を矛盾リストに記録する。
