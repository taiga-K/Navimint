# Legacy Data Dictionary

レガシーシステムのデータ構造(ER 図 + データディクショナリ)を復元するスキル。新規作り直しのエンティティ定義とデータ移行設計のインプットを作ることが目的。

## 前提条件

- 入手できる情報はソースコードと(あれば)DB スキーマのエクスポート
- ドキュメント・コメント・git 履歴・ヒアリングなし
- 機能一覧(`legacy-feature-inventory`)の CRUD マトリクスと業務用語集があれば再利用する

## 基本原則

1. **物理スキーマ(事実)と業務的意味(解釈)を分けて記録する**。カラム名・型は確定、業務的意味は出典(UI ラベル等)とともに確信度を付ける
2. **FK 制約がない前提で関係を復元する**。この年代の DB は宣言的 FK を持たないことが多く、関係は JOIN・突合条件・命名規約からの推定になる。推定根拠を必ず残す
3. コード値(マジックナンバー)は「分岐でどう使われるか(確定)」と「業務的意味(多くは推測/不明)」を分けて書く
4. 確信度 3 値は他スキルと共通: `確定` / `推測` / `不明`

## ワークフロー

```
- [ ] Phase 0: スキーマソースの確定
- [ ] Phase 1: テーブル・カラムの列挙
- [ ] Phase 2: 関係(リレーション)の復元
- [ ] Phase 3: 業務的意味の付与
- [ ] Phase 4: コード値辞書の作成
- [ ] Phase 5: 暗黙の整合性ルールの抽出
- [ ] Phase 6: 成果物の出力
```

### Phase 0: スキーマソースの確定

入手状況で 2 モードに分岐する:

- **DDL / スキーマエクスポートあり** → それを物理スキーマの正とし、コードは意味の復元に使う
- **コードのみ** → SQL 文字列・レコードセットのフィールドアクセス・INSERT 文のカラムリストからスキーマを推定する。この場合、物理スキーマ自体に確信度を付け、**「DB からのスキーマエクスポート入手」を要調査リストの先頭に置く**

### Phase 1: テーブル・カラムの列挙

- DDL があれば機械的に展開。なければ `FROM` / `INSERT INTO` / `UPDATE` 句からテーブル名を、SELECT 句・SET 句・フィールドアクセス(`rs("col_name")` / `.Fields(...)` 等)からカラム名を収集する
- ビュー・ストアドプロシージャ・トリガーも対象に含める(未入手なら要調査リストへ)
- **どのコードからも参照されないテーブル・カラム**は「廃止候補」としてマークする(削除はしない。他システムが使っている可能性があるため)

### Phase 2: 関係(リレーション)の復元

FK 制約がない場合の推定材料(優先度順):

1. **JOIN 条件**(`ON a.cust_id = b.cust_id`) — 最も信頼できる
2. **WHERE での突合**(JOIN を使わない古いコードは WHERE で結合している)
3. **アプリコード上の突合**(画面 A で取った ID で画面 B を検索する等、SQL に現れない結合)
4. **命名規約**(`cust_id` というカラム名 → M_CUSTOMER への参照と推定) — 最も弱い。単独では `推測` 止まり

多重度(1:N / 1:1)は、UNIQUE 制約・PK 構成・コードのループ構造(親 1 件に対し明細を Do While で回す等)から推定する。

### Phase 3: 業務的意味の付与

コメントなし環境でカラムの意味を復元する経路:

1. **UI ラベルとの突合(最重要)**: 画面のラベル「顧客名」の隣のテキストボックス → そのコントロールに代入される/から読まれるカラム、という対応を辿る。データバインディング定義(`DataField` / `DataBindings`)があれば機械的に対応が取れる
2. 帳票の項目名とのマッピング
3. 機能一覧の業務用語集との突合
4. カラム名からの直訳(最も弱い。`推測` とする)

意味の出典(どの画面のどのラベルか)を必ず記録する。

### Phase 4: コード値辞書の作成

1. 分岐(`Select Case` / `switch` / if)で比較されるカラムと値の組を全収集する
2. 各値について、分岐先の処理・表示される文字列(`If status = 2 Then lblStatus.Caption = "出荷済"` のような表示変換)から意味を推定する
3. **表示変換テーブル(コード値 → 表示名)がコード内にあれば、それがコード値辞書そのもの**。定数定義・変換関数・コンボボックスの初期化コードを優先的に探す
4. どの分岐にも現れない値が実データに存在しうる旨を要調査リストに書く(実データの DISTINCT 調査を推奨)

### Phase 5: 暗黙の整合性ルールの抽出

DB 制約として宣言されず、**アプリコードでのみ守られている整合性**を列挙する。データ移行設計で最重要の情報。

- アプリ側でのみチェックされる一意性・必須・範囲
- 親子の整合(親削除時に子をアプリ側で削除している等)
- 「このフラグが 1 なら必ずこのカラムに値がある」型の相関制約

ビジネスルール仕様書(`legacy-business-rules`)が既にあればルール ID を参照で紐付け、なければ本成果物内に簡潔に記録する。

### Phase 6: 成果物の出力

[output-template.md](output-template.md) のフォーマットで出力する。構成:

1. 調査サマリ
2. ER 図(mermaid erDiagram)
3. テーブル定義 + データディクショナリ
4. コード値辞書
5. 暗黙の整合性ルール
6. 廃止候補リスト / 要調査リスト

## 静的解析の死角チェックリスト

- [ ] 動的に組み立てられる SQL(テーブル名・カラム名が変数)
- [ ] 他システムが読み書きするテーブル(このコードベースに現れない利用者)
- [ ] トリガー・ストアド内でのみ使われるカラム(未入手の場合は完全に不可視)
- [ ] Access のリンクテーブル・DB リンク経由の別 DB 参照
- [ ] 実データにしか現れない値(コード値辞書の網羅性は実データで検証が必要)
