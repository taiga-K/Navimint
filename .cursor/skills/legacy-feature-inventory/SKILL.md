# Legacy Feature Inventory

レガシーコードベースから機能一覧を網羅的に復元するスキル。新規作り直しの要件定義のインプットを作ることが目的。

## 前提条件

- 入手できる情報は**ソースコードのみ**(ドキュメントなし、コメントなし、git 履歴なし)
- 開発者へのヒアリング・実機での動的解析はできない
- 言語は固定されていない(VB6 / VB.NET / C# / Delphi / C++ など混在の可能性あり)

## 基本原則

1. **網羅性はエントリポイント列挙で担保する**。「外部から呼ばれる口」(画面・操作・自動処理・帳票・連携)を全種類列挙すれば、機能の母集団は論理的に閉じる
2. **What と Why を分離する**。「いつ・どの条件で・何をするか」はコードから確定できるが、「なぜそうなのか」は復元できない。Why は「不明(要調査)」と明記して残す
3. **すべての記述に確信度を付ける**: `確定`(コードから直接読めた) / `推測`(命名や文脈からの仮説) / `不明`
4. **コードの完全な仕様書化はしない**。作り直しの要件定義に必要な粒度に留める

## ワークフロー

進捗チェックリストとして使うこと:

```
- [ ] Phase 0: 技術スタック判定
- [ ] Phase 1: 地図作り
- [ ] Phase 2: 画面の列挙
- [ ] Phase 3: 操作の列挙
- [ ] Phase 4: 語彙の収集
- [ ] Phase 5: 仮説と検証
- [ ] Phase 6: 相互検証(CRUDマトリクス)
- [ ] Phase 7: 成果物の出力
```

### Phase 0: 技術スタック判定

1. 拡張子の分布を取る: `find . -type f | sed 's/.*\.//' | sort | uniq -c | sort -rn`
2. プロジェクトファイル(`.vbp` / `.sln` / `.csproj` / `.dpr` / `.vcxproj` 等)から言語・フレームワークを特定する
3. 判定した言語に対応する節を [language-map.md](language-map.md) で読む
4. **マッピング表にない言語の場合**は後述「未知の言語への対応」に従う

### Phase 1: 地図作り

- ディレクトリ構造と命名規約を把握する(OORP "Read All the Code in One Hour": 浅く速く全体を読む)
- プロジェクトファイルの参照一覧(References / COM / DLL)を棚卸しし、**ソースが手元にない依存**をリスト化する
- 設定ファイル(App.config / INI / レジストリ読み取り箇所)を特定する

### Phase 2: 画面の列挙

機能一覧の背骨。language-map.md のパターンで画面定義ファイルを**全列挙**する。
画面以外の口も同時に列挙する: 起動点、Timer / スケジューラ、帳票定義、CLI 引数分岐、ファイル監視。

### Phase 3: 操作の列挙

各画面のメニュー項目・ボタン・イベントハンドラを列挙する。
「画面 × 操作」がほぼそのまま機能一覧の行になる。

### Phase 4: 語彙の収集

コメントがない環境での業務語彙の情報源。優先度順:

1. **UI 文字列**(Caption / Text / フォームタイトル) — 最強の語彙源
2. **メッセージ文字列**(MsgBox / MessageBox.Show / エラーメッセージ) — ビジネスルールの宝庫。「締め処理後は変更できません」の 1 行は仕様書 1 行に相当する
3. **DB スキーマ**(テーブル名・カラム名・ストアド名) — コードより腐りにくい業務語彙
4. **識別子**(関数名・変数名) — 当てにならないことがあるため 1〜3 と突合して使う

収集した語彙は用語集(output-template.md 参照)にまとめる。

### Phase 5: 仮説と検証

OORP "Speculate about Design" の反復:

1. 画面 × 操作ごとに「これは○○機能だろう」と機能名の仮説を付ける
2. イベントハンドラからコールグラフを辿り、実際の処理(DB 読み書き・ファイル出力・外部呼び出し)で仮説を検証する
3. 検証結果に応じて確信度(確定/推測/不明)を付ける

### Phase 6: 相互検証(CRUDマトリクス)

「機能 × テーブル」の CRUD マトリクスを作る。SQL は文字列リテラルとして埋まっていることが多いため、テーブル名での grep は言語非依存に効く。

- **どの機能からも書かれないテーブル** → エントリポイントの列挙漏れ、または他システムからの書き込みの疑い
- **どのテーブルも触らない機能** → デッドコード候補(作り直しスコープから外す候補)
- ストアドプロシージャ経由の読み書きも展開して含める

### Phase 7: 成果物の出力

[output-template.md](output-template.md) のフォーマットで出力する。構成:

1. 調査サマリ(対象規模・言語・確信度の分布・ソース欠落)
2. 機能一覧(本体)
3. CRUD マトリクス
4. 業務用語集
5. 要調査リスト(不明事項・死角)

## 静的解析の死角チェックリスト

調査完了前に必ず確認し、該当があれば「要調査リスト」に記載する:

- [ ] 設定ファイル / レジストリ / **DB 内の定義テーブル**による機能の有効化・分岐(設定駆動の機能は静的解析から漏れる)
- [ ] **ストアドプロシージャ・トリガー・ビュー内のビジネスロジック**(この年代のアプリはロジックの相当部分が DB 側にある。スキーマ+ストアド定義の入手を強く推奨)
- [ ] ソースのない COM / OCX / DLL 内のロジック
- [ ] リフレクション・動的な型解決・文字列組み立てによる呼び出し
- [ ] VB6 の `On Error Resume Next` で握りつぶされた分岐(字面通り読むと誤読する)

## 未知の言語への対応

language-map.md にない言語に遭遇した場合:

1. プロジェクトファイル・ビルドスクリプトから構造を推定する
2. 代表的なファイルを 1 つ精読し、4 概念(**画面 / イベント / SQL / UI 文字列**)がこの言語でどう表現されるかを特定する
3. 特定したパターンで全体を機械的に走査する
4. **判明したパターンを language-map.md に追記する**(スキルは調査のたびに育てる)
